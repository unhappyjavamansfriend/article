在資安上稱為**「憑證鏈（Certificate Chain）」驗證；而後半段關於「伺服器如何信任瀏覽器」的問題，則涉及到「雙向認證（Mutual TLS / mTLS）」**的概念。

我們把這兩個過程拆解開來看：

一、 瀏覽器如何確認你的憑證不是自簽？（憑證鏈驗證）
當瀏覽器經由 IP 找到你的伺服器，並發起 TCP 連線後，你的伺服器會把憑證丟給瀏覽器。瀏覽器這時會化身為「資安偵探」，進行以下的一連串防偽檢查：

1. 內建的「根憑證信任清單」
作業系統（如 Windows、macOS）或瀏覽器（如 Chrome、Firefox）在出廠時，內部就已經內建了一份全球信任的「根憑證機構（Root CA）」清單（例如 DigiCert, GlobalSign, Let's Encrypt 等）。這些 Root CA 的憑證是絕對信任的起點。

2. 一層一層往下找（憑證鏈）
你向憑證機構申請的憑證，通常不是由 Root CA 直接簽發的，而是由「中間憑證機構（Intermediate CA）」簽發的。這就像：
Root CA（內政部） 簽發給 -> Intermediate CA（台北市政府） 簽發給 -> 你的域名（你本人的身分證）。

當瀏覽器拿到你的憑證時，它會依序執行以下動作：

看你的憑證： 發現是由 Intermediate CA 簽名的。

追溯上一級： 瀏覽器去檢查 Intermediate CA 的憑證，發現是由某個 Root CA 簽名的。

比對信任清單： 瀏覽器檢查自己內建的清單，發現：「喔！這個 Root CA 在我的信任名單裡！」
數學驗證（公開金鑰加密）： 瀏覽器會用上一級的「公開金鑰」去解密下一級的「數位簽章」，確保這個簽名沒有被偽造或竄改。

3. 如果是「自簽憑證」會怎樣？
如果你是自簽憑證（自己當 Root CA），瀏覽器在追溯到最上層時，會發現：「這個簽發者不在我內建的信任清單裡！」
這時瀏覽器就會立刻煞車，彈出那張你很熟悉的紅色警告畫面：「您的連線不是私密連線」或「此網站的安全憑證不受信任」。

二、 伺服器要怎麼信任瀏覽器？
在標準的 HTTPS 流程中（單向認證），伺服器其實預設「不需要」信任特定的瀏覽器。
因為對大多數公開網站（如 Google、電商網站）來說，任何人來訪問都歡迎，伺服器只需要確保「傳輸通道是加密的」，讓路上的駭客偷看不到資料就好。至於瀏覽器端是誰，那是後續輸入「帳號密碼」或「API Token」時才要在應用層驗證的事情。

但如果你今天做的是高安全性系統（例如：銀行內網、金融 API 對接、微服務之間通訊），伺服器就必須嚴格確認「連進來的客戶端（瀏覽器）到底是不是合法的」。這時就會啟用 mTLS（Mutual TLS，雙向認證）。

# 雙向認證（mTLS）的運作方式：
簡單來說，就是把剛剛的流程反過來做一遍：
伺服器出示憑證： 瀏覽器驗證伺服器（剛剛講的前半段）。
瀏覽器也要出示憑證： 伺服器會向瀏覽器要求：「請出示你的客戶端憑證（Client Certificate）」。

伺服器進行驗證： 瀏覽器（或客戶端程式）發送它的憑證給伺服器，伺服器端此時也會有一套信任清單，去檢查瀏覽器憑證是不是由公司內部、或指定的 CA 所簽發的。

# 實際應用場景

一般大眾網站： 採用單向 TLS。伺服器自證清白，瀏覽器匿名訪問，後續靠帳密登入。

企業或金融 API： 採用雙向 mTLS。如果瀏覽器裡沒有預先安裝好企業發給你的專屬憑證（Client Cert），連 TCP/TLS 連線都建立不起來，直接會被伺服器拒絕於門外。
